# 联合协作实现的依据与自定规则审计（2026-09-23）

审计范围是当前 `main@b81e0b8` 加本地未提交增量，不把文献引用当成代码或物理验收。最终目标仍是同一请求经联合分配、实际 AIR/WATER 作业、必要接收、一次条件复查及规定返回，并在中文实时界面显示实际状态。本轮完成的是审计与局部纠正，**完整任务尚未实跑通过**。

## 机制依据与不能继承的结论

| 本项目采用的关系 | 直接依据 | 本项目仍须自己证明/验证 |
|---|---|---|
| 任务方法、成员、时序和运动查询交错 | [GRSTAPS，IJRR 2022](https://journals.sagepub.com/doi/full/10.1177/02783649211052066)、[D-ITAGS，RA-L 2023](https://arxiv.org/pdf/2209.13092) | 原文没有给本系统的 qn/PVS 运动资格、五平台碰撞证明或 10 秒预算保证。 |
| 执行偏差只修复受影响且未承诺的部分 | [D-ITAGS](https://arxiv.org/pdf/2209.13092)、[Calvo/Capitán，T-RO 2025 正文](https://arxiv.org/html/2411.02062v3) | 不能从论文推出当前 runner 已具备完整状态重建与复查；旧 Result、未知终态仍须锁定。 |
| 根据实际完成/接收事件释放后继，必要支援先接受 | [APEX-MR，RSS 2025](https://arxiv.org/html/2503.15836v2)、[Guo/Zavlanos，T-RO 2018](https://arxiv.org/html/1706.02092) | APEX 是装配机器人；Guo 的会合/缓存模型不能直接证明本系统 RF/声学容量或 REMUS 停止行为。 |
| 源端与移动中继分别安排开始时刻，先确认会合承诺、再由真实轨迹验证交付 | [Guo/Zavlanos 的源端/中继角色与预先协调会合](https://arxiv.org/html/1706.02092)；本仓库 `ExecutorPlanItem` 独立区间、PVS 原生路径与 `FiniteDelivery` 步首容量 | 只取“独立作业与预承诺通信机会”的组织原则，不继承论文的二维单轮车、缓冲上界或成功保证。14秒延后中继的PVS/链路隔离候选合格，但现有USV Action不能在执行前一Goal时预接纳下一段；因此生产候选仍要求参与者共同释放，提前启动试验已撤回。 |
| AIR 编队运动与海洋平台动力学使用各自原生后端 | [Swarm-Formation，ICRA 2022](https://arxiv.org/html/2109.07682v2)、[Fossen 海洋动力学模型](https://www.fossen.biz/html/marineCraftModel.html)及仓库实际源码 | Swarm 相似度不等于业务收益；原生参考合格不等于 qn 实际净距安全；PVS 模型形式不保证窄港内掉头。 |
| 观测、数据产生与接收分开 | [CARIC benchmark 正文](https://arxiv.org/html/2501.06566v2)与上述通信研究 | 本系统仅有声明的几何可见性/连续驻留代理；未校准的曝光、模糊、分辨率评分不恢复，不称真实载荷质量。 |

## 当前项目自行作出的选择

| 规则/位置 | 审计结论 | 处理 |
|---|---|---|
| `task_line.py` 曾把 `return_required` 默认解释为“回本轮起点” | **没有任务书或论文支持这个默认目的地**；REMUS 按它返航还在东栈桥前失败。 | 已删隐含起点，要求场景或调用显式声明回收/退出区的 `position` 与 `radius_m`；缺失就拒绝形成完整返回计划。此半径是业务/场景要求，不能借用 Action 的入口容差。当前联合请求没有合格回收区，保持未完成。 |
| `executors.py` AIR 支援曾额外加固定 1 秒并把 AAV 资源留到 USV 结束 | **没有来源，而且计划占用和真实锁定时间不一致**。 | 已撤销固定加秒和多余的同位置尾段 Action。产品在实际驻留合格时产生；预测用同一容量模型检查结果在预订区间内到达。受控 r6 再次实跑通过，但正向产品接收不能替代失败时的缺测通知。 |
| `task_line.py` 原水下终端等待候选 `0/30/40 s` | **不是论文数值，也不是设备参数**；30 秒方法成功不证明集合充分或最优。 | 已删除固定等待列表：由真实PVS工作/支援路线、声明的32 KiB与共享链路提出等待起点，再以0.1秒既有时间网格尝试；每个提议重新用PVS完整状态及`FiniteDelivery`核验。固定源端位置只作排序启发，**不是可证明的下界或可提交轨迹**。港口同任务选出26.5秒并实跑接收通过；不声称任意路线的最短等待。 |
| 32 KiB、8 m/2 KiB/s、30 m/32 KiB/s、0.1 s | 用户冻结的**可重复实验假设**，没有设备标定或论文给出这些装备性能。 | 保留为声明式模型；共享容量、步首因果和去重是传输逻辑要求，不宣称真实通信性能。 |
| 组件探针把 USV 初始位置设在 `(-10,4,0)`、AIR 成员固定为 AAV2 | 由同场景 RF/障碍实跑取得的**组件资格条件**，不是求解器自动选定的最终布置。 | 仅用于受控组件回归。全请求必须从场景有限位置和真实成员状态比较支援方案；60 秒诊断曾选 AAV1，不能将探针固定成员当算法输出。 |
| AIR `4 s` 保持被候选代码写死 | 请求已有 `service_time_s`，写死会使请求、Action 和 qn 查询不一致。 | 已改由请求时间驱动查询、步骤与观测区间；仍要求不短于已声明最小驻留。 |
| 10 秒共享求解期限 | 来自冻结实施计划的运行政策，**不是 GRSTAPS/D-ITAGS 的理论性能结论**。 | 保留期限；全区域请求当前在期限内返回 `PlanningBudgetExceeded`，60 秒隔离诊断得到名义方案不改写为在线通过。 |
| 把水下作业强制等到USV从前一任务释放才开始 | 仅从任务时序看没有必要；但当前Action端点一次只能接纳相应Goal，已占用USV无法同时预装下一会合片段。 | 曾以本地临时改动按成员各自 `available_from` 生成活动区间：14秒延后USV时PVS/有限交付给出两项名义合格候选，60秒诊断得到工期80.58模型秒的另一联合计划。检查runner和Action接纳边界后撤回生产改动，保留实验；先完成真实未来片段接纳合同，才可安全允许该类错峰安排。 |
| 用当前位置/介质直接重建 PVS 或 qn 后继状态 | **不成立**。`upstream/Fossen/src/python_vehicle_simulator/vehicles/{otter,remus100}.py` 的航向/深度控制保留 `e_int/psi_d/r_d/a_d/z_int/theta_int` 等状态；`qn_python_backend.py` 保留观察器、权重和执行器状态。现有Odometry与任务Result均不含这些全部状态。 | 修复时不能把同位置的新 PVS/qn 实例重置为 trim 再称“实际后继可行”。应让本机从其连续真实状态进行只读运动资格查询，或在已声明信息链路下提供足以重建且经版本核对的状态；缺该证据就保持 `UNKNOWN` 和已接受承诺。不得用母船直接读取仿真真值补齐。 |
| 把 `PlatformTaskGoal.prepare_only` 用作候选查询 | **不合适**。`pvs_node.py` 的 native preflight 确实 `deepcopy(self.backend)` 并在本机做原生查询，但 Goal 在查询前已进入 `pending`，成功后会成为已接受/预装载的资源承诺。 | 不能向执行端发一串 speculative Goal 来替代只读方法查询；这会改变 GoalID、资源占用和取消语义。若后续增加本机只读查询入口，须复用现有 preflight 的真实状态副本计算、仅返回资格/时间/终态证据，并遵守母船可接收的信息条件；该入口目前未实现。 |
| 原生观测成功Result一返回就要求母船产品已到达 | 与复制式有限容量模型及“观测／接收／释放分开”直接冲突。r4真实同运行中UUV结果先于产品回调，旧worker虽随后收到产品仍过早抛错锁定。 | 沿已有GoalID、母船收件和动作观察期限，在成功Result后有界等待正向产品，之后才提交任务结果/释放；负向继续等终结通知。r5同请求AIR＋UUV＋USV两个产品实际到达、三Result成功和资源归零。依据为本系统[有限传输实现](../../integration/qn_aav_simulator/src/qn_aav_simulator/observation_coverage.py)及[APEX实际事件释放](https://arxiv.org/html/2503.15836v2)，不借论文宣称任意网络延迟可保证成功。 |
| 旧 AIR runner 巡查后无条件附加编队、Calvo v9 排序入口 | 仅为历史控制回归，**没有当前监测业务的编队收益或生产排序依据**。 | 不作为联合任务成果；待新入口完成且确认无实际调用后清理旧算法专属代码。编队进入主搜索前须有同作业要求下的完整方法/成本或明确业务硬要求。 |

这些分类决定下一步修改的准则：论文提供**关系和方法**，上游源码提供**可执行机制**，任务模板与场景提供**业务数值**，原生动力学及同场景实跑提供**资格证据**。缺其中一项的候选保持 `UNKNOWN`；不得用界面、日志或扩大预算补成 `FEASIBLE`。
