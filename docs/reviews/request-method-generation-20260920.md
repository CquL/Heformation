# 区域请求展开与候选逐项返回

本轮把水下阶段的路径/支援方法生成移入现有任务输入代码，并保留完整请求中尚未支持的要求。没有新增在线求解器或协调节点；完整三类平台任务仍未完成。

## 请求与方法分开

`regional_requirements()`将每个区域保存为一个必做业务Task，工作域由区域类型导出。请求无需再填写AIR平台标签；旧请求的额外能力约束仍保留，旧AIR演示入口保持默认AIR语义。AIR业务允许更大执行单元进入候选资格检查，但当前尚无完整Swarm方法查询，不能据此说已完成编队比较。

`request_native_methods()`根据区域全部样点生成单锚点通过段、声明顺序及反向顺序的有限路线。每个方法均须满足该区域所有样点，实际模型和观测评价决定能否覆盖；没有先用贪心覆盖把观测位置永久固定。支援位置来自场景的communication_sites，等待候选目前沿用已验证的0/30/40秒有限集合，不称连续时间全局最优。

`build_request_executor_plan()`在一次共享预算内完成生成及原规划调用。当前只提供PVS水下/支援方法，AIR等未实现区域仍是必做任务，能力或方法不足时拒绝完整计划。未知业务字段会明确拒绝，包括尚未实现的return_required，避免输入返回要求后被悄悄忽略。旧formation_phase仍由旧入口独立处理，本增量未将它转换成新的联合方法。

## 预算与原生等待

既有私有query_worker增加逐项结果返回；规划器可以先保存一个完整解，再继续读后续方法。如果同一次查询在后续方法卡住，先前完整解仍保留。输入、输出与子进程退出受同一单调截止时刻约束，关闭搜索时清理所有查询进程。此pickle通道只用于受信任的本地规划进程，不是新的ROS接口或用户文件格式。

原生PVS允许一个完整同位置路径表示coast/trim等待，仍调用原模型积分、检查速度/介质/几何及终态时间；没有冻结位置或添加悬停控制器。退化的混合路径腿仍拒绝。查询验证至少完成400个原生积分步；此输入尚未单独新增动力学实跑，不扩大其资格范围。

## 港口接收点修正

原港口mother_ship_position位于实体船体内部，会使视线模型判定到母船的射线被自身船体遮挡。保留船体位置，另声明船外接收点(15,-8,2)，供链路评价使用；运行端和规划端一致读取。几何检查证明新点在船外，两个支援候选均有视线。没有增加距离/速率或忽略实体；该点为实验几何附件位置，不称实测天线参数。

## 实际证据

`experiments/20260920-request-methods/run-r1`使用明确命名的**水下阶段请求**（不是完整AIR/WATER请求的通过记录）：

- 从YAML通过正式输入函数生成六个方法；Noetic规划9.013169秒，预算10秒，给定有限集合搜索完成。
- 选择USV(4,8,0)、UUV等待30秒，名义方法工期99.16秒。
- 所选计划进入正式runner，原生Result、32KiB接收和资源释放全部完成。
- 全部阶段请求样点已接收；原完整请求的空中点仍未执行。

逻辑验证确认：两区域请求仍保留AIR和WATER任务；多个水下样点不被改成一条固定贪心路线；缺少AIR能力不能返回只含水下的“完整”计划。后续方法卡住时保留已取得完整解的检查通过。最终339项模块检查通过，无残留查询进程。

证据包括该目录的formal-runner-result.json、handover.bag、request-checks.log、stream-checks.log、receiver-geometry.json和all-checks.log。
